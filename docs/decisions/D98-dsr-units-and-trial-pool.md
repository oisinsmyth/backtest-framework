# D98 — DSR units contract and trial-pool semantics (audit F1/F8/F9)

**Status:** Committed
**Date:** 2026-07-14
**Category:** Validation & research integrity
**Source:** Audit remediation session (AUDIT_REPORT.md findings F1, F8, F9)

## Decision

Three coupled fixes to the study-level DSR wiring:

1. **Units (F1, the audit's one 🔴 finding).** `run_pairs_study` now logs
   `window_sharpe_daily` in per-period (daily, non-annualized) units — the previous
   code logged the *annualized* value under that name, so V[{SRn}] fed to
   `expected_max_sharpe` was in annualized² units while the observed SR was daily.
   That inflates SR0 by √252 ≈ 15.87× and forces DSR toward 0 regardless of the
   strategy (reproduced in the audit: a strategy with correct DSR 0.9996 reported
   as 0.0000). `deflated_sharpe_from_trials` now states the units contract in its
   docstring, and a regression test
   (`test_pairs_study.py::test_logged_window_sharpe_is_daily_units`) pins the
   logged metric to the observed-SR computation's units to 1e-12.

2. **Trial pool (F8).** The DSR pool is the study's **1×-cost trials only**,
   selected by a new `include` predicate on `deflated_sharpe_from_trials`
   (config/identity-based, never presence-of-metric): the same window re-run at a
   scaled cost multiplier is a cost-sensitivity point, not an additional
   independent trial — counting it five times distorted both N and V with
   near-perfectly-correlated entries. All (window × multiplier) rows remain in the
   registry (the program-level multiplicity record, D90); N for SR0 is the
   one-per-window count, reported in the artifact as such. A window with no return
   variation has no defined Sharpe estimate; the old code imputed 0.0, silently
   distorting V — now the metric is omitted, and if that happens on a 1× trial
   while a DSR is requested, the study fails loudly instead of imputing.

3. **Per-level DSR suppressed where meaningless (F9).** `run_pairs_study` gains
   `compute_dsr: bool = True`; the capacity study (and therefore the gross sweep)
   passes `False` because levels share one registry and a per-level DSR over the
   accumulated mixed pool answers no question (D95 already declared DSR "not the
   object" for those runs). `StudyResult.dsr` is `None` for such runs —
   an honest absence instead of a live wrong number.

## Rationale

D86 anchored `dsr.py` to the paper's worked example, and that implementation was
and is correct — the defect was one layer up, in how the study fed it, exactly
where no X-gate looked (the integration test asserted only `0 ≤ DSR ≤ 1`). The
published v1–v3 conclusions do not change: their observed Sharpes are negative,
so DSR = 0.0000 under both the broken and the fixed wiring — but the instrument
existed for the day a *positive* Sharpe shows up, and on that day the old wiring
would have rejected any edge unconditionally. The bias was "safe" only by
coincidence of sign.

The units mistake is worth recording as a pattern: the metric was *named*
`window_sharpe_daily` and *stored* annualized — a name asserting the very
property the value lacked. The regression test now ties the name to the
computation, per the same doc-rot discipline as D82/D91/D97.

Registry files regenerated by the study scripts after this change carry the
corrected metric; pre-fix local registry files are superseded (they contain
annualized values under the same key and must not be mixed with post-fix rows).
