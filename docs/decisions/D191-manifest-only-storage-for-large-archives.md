# D191 — For archives too large to commit, the committed artifact is the provider's own SHA256 manifest

**Status:** Committed
**Date:** 2026-08-22
**Category:** Data layer
**Source:** Provider probe ([`docs/results/binance_provider_probe.md`](../results/binance_provider_probe.md))

## Decision

Binance 1m archives are **not** committed to git. What is committed is:

1. the **manifest** — Binance's own published SHA256 for every archive used, with its key;
2. the **fetch script** that turns a manifest into local data, verifying each hash;
3. a **derived fixture at the study's own frequency**, committed in the normal way.

Raw 1m lives under `data/snapshots/` (already gitignored) or a local cache. Every study
still freezes a content-addressed snapshot and logs its id, exactly as now (D72).

## Rationale

**The numbers that force the question.** The probe measured the reachable universe at 1m:

| | |
|---|---|
| 58 reachable symbols, 1m, compressed | **6,336,384,639 bytes (6.34 GB)** |
| `BTCUSDT` alone | 230.8 MB |
| Largest currently-committed fixture | 6,654,222 bytes (6.65 MB) |
| The entire `.git` directory | 17,285,492 bytes (17.3 MB) |

The universe is **952×** the largest committed fixture and **367×** the whole repository.
`BTCUSDT` on its own is **35×** the largest committed fixture. There is no version of
"commit the fixture" that survives this.

**Why the manifest is not a retreat from immutable-by-diff, but an extension of it.** The
property D70/D24 actually buy is: *the data behind a result cannot change without a visible
diff*. Committing bytes is one way to get it. It is not the only way, and it is not the
strongest one.

A hash **we** compute over data **we** downloaded attests that we did not change it after
the fact. A hash the **provider** published attests to the same thing, and additionally:

- it is **independently verifiable** — a reader who trusts neither the repository nor its
  author can fetch the archive and check it against Binance's sidecar;
- it **cannot be regenerated by us**. Re-running a fetch and committing the new bytes
  produces a diff that looks like provenance but proves nothing about what the provider
  served. A published hash that no longer matches is a detectable event.

So the manifest is a *stronger* claim about the same bytes, made by a party with no stake
in this project's results.

**Why this is checkable rather than hoped for.** The probe measured checksum coverage on
every archive of all 58 symbols. The **minimum across symbols is 100%** — there is no
archive in the reachable universe without a published SHA256. The policy would not be
available if that number were 0.98, and the probe reports it precisely so the policy rests
on a measurement.

**Why a derived fixture is still committed.** The study's own frequency is usually not 1m,
and a 5m or 15m derivation of one universe is back inside the size regime that has worked
for eight studies. Committing it keeps the fast path — clone, run offline, get the same
numbers — while the manifest covers the base data the derivation came from. Two artifacts,
two different jobs: the fixture reproduces the *result*, the manifest reproduces the
*fixture*.

**Why not the alternatives.**

*Commit a coarser base only, never keep 1m.* Simplest, and it preserves the current
discipline literally. Rejected because it forecloses the two questions this provider was
adopted for: the S1 terrain sensor wants the finest volume available, and order-flow
imbalance is a 1m-or-finer measurement. Choosing a resolution ceiling before either
question has been asked is deciding the answer with a storage policy.

*Git LFS.* Keeps everything nominally in the repo, adds a hard toolchain dependency, and
moves the bytes out of the diff anyway — so it pays a real cost to arrive at roughly where
manifest-only already is, minus the third-party verifiability.

## Consequences

- A clone is no longer sufficient to reproduce a 1m study from scratch; it is sufficient to
  reproduce it from the committed derived fixture, and sufficient to *verify* the base data
  once fetched. That is a genuine reduction in offline self-containment and it is the
  price of the resolution.
- The fetch script must **verify every hash and fail loudly on a mismatch**, not warn. A
  provider that silently republishes an archive is precisely the event this exists to catch.
- A manifest entry is append-only in practice: adding months is a diff, and changing an
  existing entry's hash is a claim that the provider changed history, which needs saying
  out loud rather than committing.
- `SnapshotStore`'s content-addressing is unaffected. It hashes `bars.csv` + `events.json`
  (D72) and does not care where the bars came from.

## What this does not cover

Provider disappearance. If `data.binance.vision` withdraws an archive, the manifest records
what was used and proves what it was, but cannot reconstitute it. That is a real exposure
which committing bytes would not have — and the 6.34 GB is why it is accepted rather than
solved. It is recorded here so a later reader knows it was a choice.
