Golden-master hand ledger for the deposit's fund model -- iNAV, premium, creations, P9 (D611).
Companion to test_ledger_funds_ledger.py -- every number below has a matching assertion there.

Per CONTRIBUTING.md the arithmetic here was worked BEFORE the assertions were written, by a
calculator that never imports `backtest_framework`. It is also worked before any of it could be
read off a fixture, because THERE IS NO FIXTURE: the deposit's fund panel (NAV, shares
outstanding, holdings by contract month for BOIL/KOLD/UCO/SCO/UNG/USO), its ETF NBBO quotes, its
FX series and every P9 product's AUM are all listed as missing in
docs/internal/DEPOSIT_INFRASTRUCTURE_TRACKER.md. So every input below is one of two kinds:

  (a) DOCUMENT numbers -- the leverages of Section 3.1, the 5 bp and 95% of Gate 0b, c_AP =
      0.10%, the 20% restrike threshold, the 6.67% underlying move, the +$12m / +$24m of
      required unit test 26. These are the pre-registration's own figures and are cited by line.
  (b) ILLUSTRATIVE numbers -- a NAV of 100.00, a collateral yield of 5.00%, an expense ratio of
      1.00%, a held NG price of $3.00, a share count, an AUM. NOTHING HERE IS SOURCED. They are
      round numbers chosen to make the arithmetic checkable by eye, and in particular
      **y_cash = 0.05 and er = 0.01 are not any fund's actual figures**: Section 3.2 lists the
      expense ratio among the facts to source, `ledger/funds.py`'s six constants carry `er=None`,
      and `inav` RAISES on None precisely so that an illustrative number cannot leak into a
      result by being left lying around in a default.

One arithmetic choice is worth stating once, because three sections depend on it: every formula
below is evaluated LEFT TO RIGHT in the order the document writes it. `A x B x (B-1) x r` is
`((A x B) x (B-1)) x r`, not `A x (B(B-1)) x r`. The two agree to the last bit on §6's integers
and need not in general, and the tests assert `==`.

1. iNAV -- REQUIRED UNIT TEST 14
================================================================================
Illustrative inputs, stated as such in the preamble:

    NAV_f[t-1]   100.00        (per share)
    y_cash       0.05          (5.00% annual, ACT/360)
    ER_f         0.01          (1.00% annual, ACT/365)

The accrual term, which is the same in every case below:

    y_cash / 360 = 0.05 / 360   = 0.0001388888888888889
    ER_f   / 365 = 0.01 / 365   = 2.7397260273972603e-05
    accrual      = 0.0001388888888888889 - 2.7397260273972603e-05
                 = 0.00011149162861491629

THE TWO DAY COUNTS ARE DIFFERENT AND THAT IS THE DOCUMENT'S OWN ARITHMETIC (line 184). Written
both on 365 the accrual would be

    0.05 / 365 - 0.01 / 365 = 0.00013698630136986303 - 2.7397260273972603e-05
                            = 0.00010958904109589043

which is 1.7% smaller than the document's 0.00011149162861491629 -- invisible on a day and a
one-way drift over a sample, spending part of Gate 0b's 5 bp budget on a day count.

(a) ZERO MOVE, r_held = 0. Required unit test 14's first clause: "iNAV with zero futures move
    equals NAV[t-1] x (1 + accruals)".

        iNAV = 100.0 x (1 + L x 0.0) + 100.0 x 0.00011149162861491629
             = 100.0 + 0.011149162861491629
             = 100.01114916286149

    and NAV[t-1] x (1 + accrual) = 100.0 x 1.0001114916286149
                                 = 100.01114916286149

    THE SAME DOUBLE, asserted with `==`. That is a property of these three numbers and not of
    the algebra: `a + a*x` and `a*(1+x)` are different roundings in general, and the pair was
    chosen so that the test can be an equality rather than a tolerance. The value of L does not
    matter here (L x 0.0 is 0.0 for every finite L), and the test runs it at L = +2 and L = -2.

(b) L = +2, r_held = +0.01. "with L = 2 and r = +1% it rises about 2%":

        levered part = 100.0 x (1 + 2 x 0.01) = 100.0 x 1.02 = 102.0     (exact)
        iNAV         = 102.0 + 0.011149162861491629
                     = 102.01114916286149
        total return = 102.01114916286149 / 100.0 - 1
                     = 0.02011149162861492        (+2.011%)

    "About 2%" is +2.011%, and the 0.011% is the accrual, not slippage in the leverage: the
    test asserts the levered part is exactly 102.0 and names the accrual as the remainder.

(c) L = -2, r_held = +0.01. "with L = -2 it falls about 2%":

        levered part = 100.0 x (1 - 0.02) = 98.0                          (exact)
        iNAV         = 98.0 + 0.011149162861491629 = 98.01114916286149
        total return = -0.019888508371385116       (-1.989%)

    The inverse fund falls by slightly LESS than 2% and the difference is the same accrual
    working the other way relative to the move. A test asserting |return| = 2% on both sides to
    four decimals would fail on this line and be right to.

(d) L = +1 (UNG, USO), r_held = +0.01:

        iNAV = 101.0 + 0.011149162861491629 = 101.01114916286149

    and the rebalance factor L(L-1) = 1 x 0 = 0 exactly -- required unit test 2's arithmetic,
    which is why these two funds are "creations only" (line 64).


2. GATE 0b -- REQUIRED UNIT TEST 20
================================================================================
The error per day, in basis points of the OFFICIAL NAV:

    bp = (iNAV_at_settlement - official_NAV) / official_NAV x 1e4

Twenty days. Official NAV is 1000.00 every day (illustrative, and round so the bp arithmetic is
readable). iNAV at settlement:

    days 1..19   1000.20      ->  bp = 0.2000000000000455 / 1000.0 x 1e4 = 2.0000000000004547
    day 20       1000.80      ->  bp = 0.7999999999999545 / 1000.0 x 1e4 = 7.999999999999545

    (The trailing digits are the decimal-to-binary conversion of 1000.2 and 1000.8, not an
    error in the division: 1000.2 - 1000.0 is not 0.2 in doubles. Nothing here sits near the
    5 bp line, so the comparison is decided by the leading digit either way.)

    within 5 bp: 19 of 20        share = 19 / 20 = 0.95
    the bar    : >= 0.95         0.95 >= 0.95    -> PASSES

THE PASS IS EXACTLY ON THE BOUNDARY AND THAT IS THE POINT. 19/20 = 0.95 is representable
exactly, so `share_within >= 0.95` is decided by the document's own inclusive ">=" and not by a
rounding. A gate written with `>` would fail this case, and 19 good days in 20 is precisely what
line 191 permits.

    Second case: days 19 AND 20 at 1000.80  ->  18 of 20 = 0.90  ->  FAILS.
    Third case, the limit itself: 1000.50 -> bp = 5.0 EXACTLY, and 5.0 <= 5.0 is within.
    Fourth: 999.40 -> bp = -6.000000000000227, beyond the limit on the LOW side. The sign is
    kept in the output and only |bp| is compared.

    worst |bp| in case 1 = 7.999999999999545.

Three refusals, each with its own message: unequal lengths (19 iNAVs against 20 NAVs), an empty
sample (which would "pass" 0 of 0 vacuously), and an official NAV <= 0 (which would turn a
broken panel row into a plausible error in bp).

4. STRESS (line 211)
================================================================================
The trailing 60 days of prem_twa, all prior to the day being scored:

    30 days at 0.001 and 30 days at 0.003      (illustrative)

    |values| mean = (30 x 0.001 + 30 x 0.003) / 60 = 0.12 / 60 = 0.002
    deviations    = +/- 0.001 on every day
    variance      = 60 x (0.001)^2 / (60 - 1) = 6e-05 / 59 = 1.0169491525423728e-06
    sd (ddof = 1) = 0.0010084389681792214

    stress(prem_twa = +0.004) = (0.004 - 0.002) / 0.0010084389681792214
                              = 1.9832633040858023

    stress(prem_twa = -0.004) is the SAME number: line 211 z-scores |prem_twa|.
    stress(prem_twa = +0.002) = 0.0 exactly.

TWO REFUSALS THAT ARE NOT ARITHMETIC. A trailing entry dated on or after the scored day raises
-- the window is prior days only, and today's own premium in its own reference distribution
pulls the z toward zero on exactly the days the feature exists to flag (R9's shape, in a
feature rather than in an anatomy). And a constant trailing window raises, because sd = 0 has no
z-score and a clipped one would report a finite stress from no dispersion at all.

5.4 The hedged fraction (line 232) -- REQUIRED UNIT TEST 18. h0 = 1.0, h1 = 0.5 (illustrative;
    both are Stage C2 fitted parameters and nothing has fitted them):

      stress   x = h0 - h1 x stress      h = 1 / (1 + exp(-x))
      -2.0     +2.0                      0.8807970779778823
       0.0     +1.0                      0.7310585786300049
      +2.0      0.0                      0.5                    (exactly, at x = 0)
      +4.0     -1.0                      0.2689414213699951

    Strictly decreasing in stress, every value strictly inside (0, 1): "h1 >= 0: more stress ->
    less hedged". Note 1 - 0.7310585786300049 = 0.2689414213699951 exactly on these doubles.

    h1 = 0.0 is the FLAT case and is permitted (line 472 is h1 >= 0, not h1 > 0): h is
    0.7310585786300049 at every stress.

    h1 = -0.1 RAISES. A negative h1 is the opposite mechanism -- more stress, more hedged --
    wearing a fitted coefficient.

    P3.7 (line 271), the attention term: h0 = 1.0, h1 = 0.5, stress = 0.0, g1 = 2.0,
    att_accel = 1.0 gives 0.0 + 2.0 x 1.0 = 2.0 in place of stress, hence x = 0.0 and h = 0.5 --
    the same cell as stress = +2.0 above, which is what "replace stress with stress + g1 x
    att_accel" means. g1 = -0.1 RAISES (line 472).

    SATURATION. The logistic is in the OPEN interval mathematically and a double reaches 1.0 at
    about x = 37 (1/(1+exp(-36)) is 0.9999999999999998 and 1/(1+exp(-37)) is 1.0). h0 = 40.0
    therefore RAISES rather than returning 1.0: at h = 1.0 the entire creation flow is declared
    already hedged intraday, which is a statement about floating point and not about a market.

5.5 The split (lines 233-234), at Create_flow = +666.6666666666666 and h = 0.7310585786300049:

    Q3_window   = (1 - h) x flow = 0.2689414213699951 x 666.6666666666666 = 179.29428091333006
    Q3_intraday =      h  x flow = 0.7310585786300049 x 666.6666666666666 = 487.3723857533366
    sum         = 666.6666666666666        -- the same double as the flow, on THESE numbers

    CONSERVATION IS NOT EXACT IN GENERAL and the test says so rather than hiding it. The legs
    are computed as the document writes them, `(1-h) x flow` and `h x flow`, not one as the
    residual of the other; two roundings need not sum back. The canonical counterexample in
    doubles is 0.7 + 0.3 = 0.9999999999999999. It holds exactly here, and the property test
    asserts conservation to within four ulp of the flow rather than asserting an equality that
    is a coincidence of this pair.

    At flow = -666.6666666666666 the two legs are -179.29428091333006 and -487.3723857533366:
    the split never changes a sign, it only divides one.

7. THE RESTRIKE -- REQUIRED UNIT TEST 29
================================================================================
Line 292, for a +3x WisdomTree product. The threshold is on the PRODUCT's intraday value (20%);
the "about 6.67%" is the UNDERLYING move that reaches it, 0.20 / 3 = 0.06666666666666667.

Last reset level = 100.00 (the product's value at its prior reset; illustrative).

    value(r_underlying) = 100.0 x (1 + 3 x r_underlying)

    r = -0.067:  100.0 x (1 - 0.201) = 79.89999999999999
                 drawdown = (79.89999999999999 - 100.0) / 100.0 = -0.2010000000000001
                 -0.2010000000000001 <= -0.20   ->  RESTRIKE, new reset level 79.89999999999999

    r = -0.065:  100.0 x (1 - 0.195) = 80.5
                 drawdown = -0.195
                 -0.195 > -0.20                 ->  NO EVENT

    THE BOUNDARY, inclusive: a product value of exactly 80.0 gives a drawdown of exactly -0.2
    and DOES fire ("falls by the threshold" is read as at or beyond it).

    THE SHORT PRODUCT: for -3x the adverse move is a RISE. r = +0.067 gives
    100.0 x (1 - 0.201) = 79.89999999999999, the same arithmetic and the same event -- what
    falls is the product, not the underlying, in both cases.

AFTER THE RESTRIKE (line 292: "the settlement-window flow is recomputed from the restrike
level"). AUM at the restrike $20,000,000 (illustrative), L = 3:

    a further -1% in the underlying from the restrike:
        20000000.0 x 3.0 x 2.0 x -0.01 = -1200000.0          (-$1.2m, a sell)
    a +2% recovery from the restrike:
        20000000.0 x 3.0 x 2.0 x  0.02 = +2400000.0          (+$2.4m, a buy)

    Both are the line 284 formula with the AUM and the return measured FROM the restrike. Using

    once in the intraday forced trade and again in the window.

THE LOG (line 294). `restrike_events.csv`, three columns, written ONLY to a path the caller
names:

    timestamp,product,estimated_dH
    2026-09-18T13:47:00,3NGL,-1200000.0

    An event with no timestamp or no product cannot be added -- the row is defined by line 294
    and a row missing two of its three fields is not that row. An `estimated_dH` of None is
    written as the EMPTY string, never as 0.0: nobody computed it, which is not the same as
    computing zero. Writing over an existing file raises.


8. WHAT NONE OF THIS IS
================================================================================
No fund has an expense ratio here, no product has an AUM, no day has an FX rate, no minute has a
real quote, and no parameter (h0, h1, g1, n9, a0..a3, b1..b4) has been fitted to anything. The
deposit's Gate 0b has not been run, because running it needs a point-in-time fund panel that
docs/internal/DEPOSIT_INFRASTRUCTURE_TRACKER.md records as missing. What is checked above is
that the arithmetic those data will be poured into is the arithmetic the document specifies, at
the numbers the document itself states, with every place a fact is absent RAISING rather than
defaulting.
