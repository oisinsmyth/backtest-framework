D609 -- the panel loader chokepoint. Hand-computed ledger.
==========================================================

Written before `tests/golden/test_panels_ledger.py`. Every number below is derived from a
source that existed before `src/backtest_framework/data/panels.py` did -- the committed
artefact `data/d555_tsmom_replication.json`, the committed manifest `data/data_manifest.json`,
and `scripts/run_d555_tsmom_replication.py`'s own `load_fixture()` compiled out of its source
and run. The golden asserts that the loader reproduces them; it does not define them.


SS1. THE FIXTURE DIGEST, REPRODUCED ON D555'S OWN PUBLISHED NUMBER  (R16)
-------------------------------------------------------------------------
`frozen.sha256_file(path, text_normalise=False)` is documented as bit-identical to
`build_data_manifest.py:63 sha256_of` and to `run_d555_tsmom_replication.py:79 sha256`. Three
routes, one number, and it is published:

  data/d555_tsmom_replication.json   "fixture_sha256"
      c64dfe70211242368772da005e05e11ed2f2e779e6599d0e0a6a2bbabee355de

  data/data_manifest.json            files[path == "data/fixtures/fut_breadth_hourly.csv.gz"].sha256
      c64dfe70211242368772da005e05e11ed2f2e779e6599d0e0a6a2bbabee355de

  LoadedPanel.sha256 for load_panel("fut_breadth_hourly", reserved_from="2024-01-01")
      c64dfe70211242368772da005e05e11ed2f2e779e6599d0e0a6a2bbabee355de

Three equalities, not one: the loader agrees with the manifest (which is what it asserts on
every read) AND with a number D555 published on 2026-09-19, so the panel under the loader is
the panel that study scored.


SS2. THE ROW COUNT, AGAINST run_d555.load_fixture()
----------------------------------------------------
`load_fixture` (`run_d555_tsmom_replication.py:87-120`) does three things: it reads five
columns plus the 23 hourly closes, it cuts the reserved slice at line 98
(`df = df[df["day"] < RESERVED_FROM]`), and it then DROPS two classes of row that are not
sessions -- placeholder rows with no finite close, and weekend-dated stubs. It records both
counts in `df.attrs`.

`load_panel` does the cut and nothing else, which is correct: dropping a non-session is a
study's judgement about its own fixture, not a property of the file. So the two row counts are
not equal and must not be asserted equal. The identity that holds is the runner's own
arithmetic, and it holds EXACTLY:

    load_panel rows                       140,814
  - attrs["rows_dropped_no_close"]         22,531
  - attrs["rows_dropped_weekend_stub"]          69
  ------------------------------------------------
  = run_d555.load_fixture() rows          118,214      (118,214 == 118,214)

  frame["day"].max()   load_panel  '2023-12-29'
                       run_d555    '2023-12-29'        equal, as strings

  frame["day"].min()   load_panel  '2010-06-07'
                       run_d555    '2010-06-07'        equal, as strings

The `max` agreeing is not implied by the counts: it says the LAST session survives both of
D555's drops, so the cut is the binding constraint at the right-hand end in both routes.


SS3. THE WINDOW RECORD
-----------------------
`frozen.window_record`'s six keys, for the same call:

  first_session_read        '2010-06-07'
  last_session_read         '2023-12-29'
  reserved_from             '2024-01-01'
  sessions_read             140814        (rows, one per (root, day))
  distinct_sessions_read      4217        (distinct days)
  reserved_rows_read             0         asserted 0 by layer 2 as well

4,217 distinct days against D555's own `windows` block -- 3,353 sessions on the long window
(2011-01-03..2023-12-29) and 2,065 on the primary (2016-01-04..2023-12-29). 4,217 is larger
than both and must be: it counts every day in the file from 2010-06-07, including the Sundays
and holidays `load_fixture` drops and the pre-2011 days neither window covers.


SS4. THE MERGE, NOT THE REPLACEMENT
------------------------------------
`data/d555_tsmom_replication.json`'s `"windows"` block carries six keys:

  primary, long, reserved_from, sessions_primary, sessions_long, month_ends

and `window_record`'s six are

  first_session_read, last_session_read, reserved_from, sessions_read,
  distinct_sessions_read, reserved_rows_read

The intersection is exactly {reserved_from}, and both say '2024-01-01'. So
`LoadedPanel.windows_update` on D555's committed block yields 6 + 6 - 1 = 11 keys, with
`primary`, `long`, `sessions_primary`, `sessions_long` and `month_ends` untouched. A loader
that REPLACED the block would delete five keys D555's pre-registration names.

A second read whose `reserved_from` differs raises rather than overwriting.


SS5. THE PANEL THAT IS ENTIRELY RESERVED
-----------------------------------------
`data/fixtures/fut_book_depth_1m.csv.gz` (D604) spans 2026-08-11..2026-09-09. Under
`reserved_from="2024-01-01"` and no word:

  rows                          0
  first_session_read         None
  last_session_read          None
  sessions_read                 0
  distinct_sessions_read        0
  reserved_rows_read            0

Zero rows is the correct answer and it is the case that proves `reserved_from` must have no
default: the same file is INSIDE the deposit's sealed vault window (2025-03-01..2026-09-18)
and AFTER this repository's seal, and `costs/futures_impact.py:361 depth_bar` reads it by
passing `reserved_from = day`, which asserts nothing. Reconciling the two windows is the
principal's decision and this loader does not make it.
