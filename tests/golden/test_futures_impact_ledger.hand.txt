Golden-master hand ledger for the futures square-root impact brick.
Companion to test_futures_impact_ledger.py; every number below has a matching assertion there.

The arithmetic was worked without importing `backtest_framework`. The inputs are of two kinds:

  (a) Measured numbers, read from the committed artefact `data/futures_impact_params.json` by
      key path. They are quoted at full repr precision so that they reproduce exactly; a sigma
      rounded to six digits would not.
  (b) Declared numbers: Y = 0.7 and the depth exponent 0.5. These are modelling choices, not
      measurements. Y = 0.7 lies inside the 0.5-1 range reported for stocks and futures by
      Tóth, Eisler and Bouchaud (2016, arXiv:1602.03043); it is fixed, not fitted.

The committed artefact is the source of the measured numbers; no figure is taken from the
module under test.


0. THE TWO FORMULAS
================================================================================
Square-root impact ("predicted move"):

    V_d   = 20-day trailing mean daily volume of the traded contract (days t-20 ... t-1)
    sigma_d = 20-day trailing daily return std
    I     = Y * sigma_d * sqrt(|Q_rem| / V_d) * P * sign(Q_rem)        (price units)
    SNR   = |Q_rem| / sigma_rem

    Y = 0.7, fixed.

Depth-based impact:

    I_D = Y * sigma_d * sqrt(|Q_rem| / V_d) * P * sqrt(D_bar / D(t0)) * sign(Q_rem)
          (Y = 0.7 fixed; exponent 0.5 fixed)

In this repository's names:

    impact_fraction(f, Q)      = Y * sigma_fraction * sqrt(|Q| / adv_contracts)   [dimensionless]
    impact_for_flow(f, Q, P)   = sign(Q) * impact_fraction * P                    [price points]
    impact_usd(f, Q, P)        = impact_fraction * |Q * P * usd_per_point|        [dollars]
    depth_scaled(I, D, D_bar)  = I * sqrt(D_bar / D)                              [same units]

Section 2 asserts equality with `==`, so the evaluation order is part of the contract:
`coefficient * sigma * sqrt(|Q| / adv)`, left to right, the divide inside the sqrt.


1. THE MEASURED LINE
================================================================================
data/futures_impact_params.json # roots.ES.lines.day1m_2016_2023

    window            2016-01-04 .. 2023-12-29        (ends before 2024-01-01)
    sessions          1975
    adv_contracts     1253830.165063291
    sigma_fraction    0.00932119101946498
    sigma_usd_per_contract   1519.9726384933488
    notional_usd      163066.35443037972
    usd_per_point     50.0

The division that defines sigma_fraction, checked by hand:

    1519.9726384933488 / 163066.35443037972 = 0.00932119101946498

This equals the stored value bit for bit and is asserted with `==`.

The ES contract itself (data/futures_contract_specs.json; written out rather than read, so
the golden test does not share its inputs with the code):

    ES   tick_points 0.25   usd_per_point 50.0   tick_usd 12.5

Declared: Y = 0.7. This differs from `costs/equity_bricks.py:SqrtImpact`'s default of 1.0;
a futures brick using 1.0 would charge 1/0.7 = 1.428... times the declared law.


2. IMPACT FRACTION, HAND-WORKED
================================================================================
Q = 1,000 ES contracts.

    ratio = 1000.0 / 1253830.165063291
          = 0.0007975561825389021

    sqrt(ratio)
          = 0.02824103720720792

    fraction = 0.7 * 0.00932119101946498 * 0.02824103720720792
             = 0.00018426807167734195

    in basis points of the price:  1.8426807167734196 bp

Two more points, to check the shape of the curve:

    Q = 1 contract          ratio 7.975561825389021e-07
                            sqrt  0.000893060010603376
                            fraction 5.827068065475641e-06

    Q = 4,000 contracts     ratio 0.0031902247301556085
                            sqrt  0.05648207441441584
                            fraction 0.0003685361433546839

Quadrupling Q doubles the fraction, and for these doubles it does so exactly in binary:

    2 * 0.00018426807167734195 = 0.0003685361433546839

(That exactness is a property of these particular doubles, not of the law. The test asserts the
sqrt-scaling relation with `==` only on this pair, and the general shape by ratio elsewhere.)


3. DOLLARS AND SIGNED POINTS
================================================================================
At P = 4,000.00 index points, Q = 1,000 ES:

    notional = 1000.0 * 4000.0 * 50.0 = 200000000.0          ($200,000,000)

    impact_usd       = 0.00018426807167734195 * 200000000.0
                     = 36853.61433546839                      ($36,853.61)

    impact_for_flow  = +0.00018426807167734195 * 4000.0
                     = 0.7370722867093678                     (+0.737 index points on a BUY)

    and for Q_rem = -1,000:
                     = -0.7370722867093678                    (the same magnitude, negated)

Sign and zero, both asserted:
    (a) sign follows Q_rem                -> the pair above, equal and opposite;
    (b) zero Q_rem gives zero I           -> impact_for_flow(f, 0.0, P) = 0.0 exactly,
                                             and for -0.0 as well.

One ES is $200,000 of index at 4,000 and one MES is $20,000; the fraction is the same at
either size, and only the notional it is charged on changes. So
`data/futures_impact_params.json` stores each root's `size` block
(roots.ES.size.size_ratio_full_over_sized = 10.0, usd_per_point_sized = 5.0 ), and a quantity
in micros must be converted before it is divided by a full-size ADV.


4. THE DEPTH SCALING, AND THE IDENTITY
================================================================================
    depth_scaled(I, D, D_bar) = I * sqrt(D_bar / D)

Identity: I_D = I when the book is at its usual depth.

    D(t0) = D_bar  =>  D_bar / D = 1.0 exactly (any finite positive double over itself)
                   =>  sqrt(1.0) = 1.0 exactly
                   =>  I * 1.0   = I exactly, for every finite I including 0.0 and negatives.

So the assertion uses `==`, not `approx`. Checked by hand on all three of Section 3's
quantities at D = 54927.0 (an ES-sized book), at D = 1.0 and at D = 1e12:

    0.00018426807167734195  ->  0.00018426807167734195
    0.7370722867093678      ->  0.7370722867093678
    36853.61433546839       ->  36853.61433546839

Direction, since a ratio is easy to invert: a book thinner than usual costs more.

    D = 25, D_bar = 100   ->  sqrt(4)    = 2.0    ->  I doubles
    D = 400, D_bar = 100  ->  sqrt(0.25) = 0.5    ->  I halves
    I = -10, D = 25, D_bar = 100          ->  -20.0     (the sign is preserved)

Applied to Section 2's Q = 1,000 fraction in a book at a quarter of its usual depth:

    0.00018426807167734195 * 2.0 = 0.0003685361433546839

This is the same double as the Q = 4,000 fraction in Section 2: a coincidence of these
numbers, not an identity.

6. THE SAME LAW AS THE EQUITY BRICK
================================================================================
`costs/equity_bricks.py:SqrtImpact.impact_fraction` computes

    self.coefficient * params.sigma_daily * math.sqrt(abs(quantity) / params.adv_shares)

which is the same expression with `sigma_daily` for `sigma_fraction` and `adv_shares` for
`adv_contracts`. Given the same two doubles and the same coefficient, both return the same
double; the golden test asserts this on Section 2's numbers with `==`.

A separate class exists because `SqrtImpact._params_for` reads `instrument.symbol`, and
`instruments/future.py:Future` carries `root` and has no `symbol`, so `SqrtImpact` applied
to a Future raises. That raise is also asserted.


7. BRICK_KEYS ROW
================================================================================
`config/cost_stack.py:BRICK_KEYS` has exactly one row for this brick:

    "futures_sqrt_impact": frozenset({"type", "root", "coefficient", "line"})

The nine rows that existed before it (the eight equity and generic rows plus
`futures_round_trip`) are unchanged. Transcribed from cost_stack.py before the row was added:

    flat_commission     {type, amount}
    percent_spread      {type, bps}
    ibkr_commission     {type, per_share, min_per_order, max_pct_of_trade_value}
    borrow_fee          {type, annual_rate}
    margin_interest     {type, annual_rate}
    flat_rate_carry     {type, annual_rate}
    sqrt_impact         {type, coefficient, calibration, volume_units}
    dividend_flow       {type, source}
    futures_round_trip  {type, commission_rt_usd, crossing_ticks_rt, root, line}

The assertion checks that adding a tenth row removed no key from any of the nine, which would
make a stored config fail to load.

`futures_sqrt_impact` has no explicit form (no `adv_contracts` / `sigma_fraction` keys): an
ADV and a sigma written into a config would have no measurement window or provenance, which
data/futures_impact_params.json provides.


8. THE ARTEFACT'S OWN SHAPE
================================================================================
data/futures_impact_params.json, top level:

    default_line      "day1m_2016_2023"
    coefficient_Y     0.7
    roots             36
    lines             trades_2025_2026 (9 roots), hourly_2010_2026 (36, NO volume), day1m_2016_2023 (36)
    complete_lines    ["trades_2025_2026", "day1m_2016_2023"]

`hourly_2010_2026` carries a sigma and a notional but no `adv_contracts`, because its source
data has no volume field. The brick raises on that line at construction. The measurement is
stored with the gap and rejected at the point of use, rather than dropping a measured sigma
or filling the ADV from another window.

The default is the 2016-2023 line. The other two are measured on 2025-09..2026-09, so a
backtest over earlier years using them would be charged with parameters measured after its
own window.
