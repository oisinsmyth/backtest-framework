WHAT IS BEING PINNED, AND WHY IT IS A GOLDEN AND NOT A UNIT TEST
---------------------------------------------------------------
A forward recorder's whole value is that a file written today is still the same file,
and still says the same thing about WHEN it arrived, in two years' time when a
forward test reads it. Three quantities carry that and each one is an exact string:

  * the CHECKSUM of the bytes as they arrived (§13A.3: "Store a checksum per file");
  * the FILENAME, because the filename carries `fetched_at` and because a second
    fetch must produce a SECOND NAME rather than a replacement (unit test 31);
  * the GAP LINE, because `data/recorder/GAPS.md` is the artefact a human reads to
    learn that a window closed empty, and it is appended to forever (unit test 33).

Two independent SHA-256 implementations were used and agreed on every line:

  (a) GNU coreutils `sha256sum` (Git Bash), fed by `printf` so the exact bytes are
      visible in the command;
  (b) .NET `System.Security.Cryptography.SHA256` driven from PowerShell over a
      literal `[byte[]]` array, so the input is written as hex octets and no text
      encoding or newline translation can intervene.

Anchor, to prove (a) and (b) are standard SHA-256 before anything else is trusted:

    $ printf '' | sha256sum
    e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855

    PS> $sha.ComputeHash([byte[]]@())
    e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855   (len 0)

which is the published SHA-256 of the empty string. Case 0 asserts it.

THE RESPONSE BYTES ARE NEVER NORMALISED, AND THAT IS THE DIFFERENCE FROM D594.
D594's `sha256_file` LF-pins text before hashing, because code is text and a
checkout's newline handling must not move a frozen identity. **A recorded response
is not source.** It is what a server sent, and normalising it would mean the bytes
on disk no longer hash to the checksum beside them. So every digest below is over
the bytes EXACTLY as handed to `record()`, and the payloads in this ledger are
written to disk with `write_bytes` from explicit literals, never `write_text`.

Case 1 — UNIT TEST 31. THREE RECORDS, THREE FILES, AND NOTHING OVERWRITTEN.
================================================================================
Ledger doc §13A.3: "**Never overwrite.** New fetches are new files. Store a
checksum per file." Unit test 31: "Recorder never overwrites: a second fetch on the
same day creates a new file; checksums differ only if content differs."

The job is `bls_cpi`, the key is `bls_cpi`, the extension is `html`, and the clock
is driven by hand so the stamps are exact. Three calls to `record()`, in order:

  #  clock (UTC)             payload      filename
  -  ----------------------  -----------  ------------------------------------
  1  2026-09-21T14:30:00Z    PAYLOAD 1    bls_cpi__20260921T143000Z.html
  2  2026-09-21T14:30:00Z    PAYLOAD 1    bls_cpi__20260921T143000Z-1.html
  3  2026-09-21T14:31:00Z    PAYLOAD 2    bls_cpi__20260921T143100Z.html

  THE NAMING RULE, spelled out because the second row is the whole test.
  `{key}__{YYYYMMDDTHHMMSSZ}.{ext}` is `scripts/fetch_release_calendar.py:193`'s
  filename, unchanged. The stamp resolves to the SECOND, so two records inside one
  second would collide; the collision is resolved by appending `-1`, `-2`, ... to
  the stamp, NEVER by writing over the file that is there. Record 2 therefore has:

      a DIFFERENT path from record 1   (…143000Z-1.html vs …143000Z.html)
      the SAME sha256 as record 1      (f06956244779abde350c97ff5e18c909ea39bdbb7a9894d026fa1ac3600c6a34)
      the SAME fetched_at as record 1  (2026-09-21T14:30:00Z)

  and record 1's bytes on disk after all three calls are still, byte for byte,
  b"schedule v1\n", hashing to f0695624.... The suffix lands on the STAMP and not
  after the extension, so every file in the directory still ends `.html`.

  CORRECTION, AND IT IS WHY THIS LEDGER IS WRITTEN BEFORE THE CODE. This case was
  first written claiming that "a chronological sort of the names is still a sort by
  fetched_at". THAT IS FALSE INSIDE ONE SECOND, and the golden caught it on the
  first run. `-` is 0x2D and `.` is 0x2E, so

      bls_cpi__20260921T143000Z-1.html   <   bls_cpi__20260921T143000Z.html

  lexicographically: record 2 sorts AHEAD of record 1. Across different seconds a
  name sort IS a time sort, because the stamp is fixed width and zero padded
  (…143000Z-1 < …143100Z holds, on the fifth time digit). So the rule is:

      a name sort orders records correctly BETWEEN seconds and not WITHIN one,

  and `Recorder.records` therefore sorts on `(fetched_at, collision index, path)`
  with the index extracted as a NUMBER, which makes the read order the write order.
  The claim is corrected here rather than deleted, because the wrong version is what
  a reader would have assumed.

  Record 3 is the content change: a new second, so no suffix, and the digest moves
  to ccd1d9f0....

  Manifest after the three calls (the per-job `_manifest.json`), in order, one
  entry per file, each carrying its own checksum:

      [0] bls_cpi__20260921T143000Z.html     f0695624...  2026-09-21T14:30:00Z
      [1] bls_cpi__20260921T143000Z-1.html   f0695624...  2026-09-21T14:30:00Z
      [2] bls_cpi__20260921T143100Z.html     ccd1d9f0...  2026-09-21T14:31:00Z

  3 entries, 2 distinct digests, 3 distinct paths.

Case 2 — UNIT TEST 32. AVAILABILITY IS `fetched_at`, AND IT IS THE LATER NUMBER.
================================================================================
Ledger doc §13A.3: "For forward tests, **`fetched_at` is the availability time**
(conservative; decision D23)." Deposit decision D23: "`fetched_at` used as
availability time in forward tests — Conservative: publication timestamps can be
optimistic."

Not arithmetic, but pinned here because the direction of the inequality is the
finding and a sign error would be invisible in a unit test that used one timestamp.

  a record of the CPI release page:

      published_at : 2026-09-18T08:30:00Z     (what the source states)
      fetched_at   : 2026-09-21T14:30:00Z     (when these bytes arrived here)

      availability_time(record) == "2026-09-21T14:30:00Z"

  The two differ by 3 days, 6 hours — 280,800 seconds — and the answer is the LATER
  of them. A forward test that used `published_at` would be claiming the data was
  usable three days before this machine held it. `availability_time` therefore
  returns `fetched_at` UNCONDITIONALLY: it does not compare, it does not take a
  maximum, and it does not fall back to `published_at` when that field is None —
  because a rule with a branch in it is a rule that can take the wrong branch.

  `published_at` is recorded ONLY when the caller passes it, and is `null` in the
  manifest otherwise. It is never inferred from a `Date:` or `Last-Modified:`
  header, never from the filename, and never from the document's own text.

Case 3 — UNIT TEST 33. THE GAP TABLE FOR A TWO-JOB SYNTHETIC SCHEDULE.
================================================================================
Ledger doc §13A.3: "Gap detection: alert if any daily job misses its window. Log
gaps in `data/recorder/GAPS.md`. Gaps are **never** filled with estimates."

THE SCHEDULE. Two jobs, both `status: ready`:

  job            cadence  weekday   window (ET)      window in UTC (see below)
  -------------  -------  --------  ---------------  -------------------------
  daily_probe    daily    —         09:00 - 17:00    13:00Z - 21:00Z, same day
  weekly_probe   weekly   Fri (4)   15:30 - 23:00    19:30Z - 03:00Z, next day

  THE UTC CONVERSION, done by hand. Every date below is in September 2026, which is
  inside US Eastern Daylight Time, so ET = UTC-4 and a wall-clock ET time converts
  by adding 4 hours:

      09:00 ET + 4h = 13:00 UTC   (same calendar date)
      17:00 ET + 4h = 21:00 UTC   (same calendar date)
      15:30 ET + 4h = 19:30 UTC   (same calendar date)
      23:00 ET + 4h = 03:00 UTC   (the NEXT calendar date — this one rolls over)

  The window is CLOSED-CLOSED: a record whose fetched_at equals the open instant or
  the close instant counts. The conversion is done through the IANA zone
  `America/New_York` and not by adding a constant, so a window in November converts
  by five hours without any special case.

  THE SPAN. `since` = 2026-09-16 (ET), `now_utc` = 2026-09-22T04:00:00Z, which is
  2026-09-22 00:00 ET. The weekdays, from the civil calendar:

      2026-09-16 Wed   2026-09-17 Thu   2026-09-18 Fri   2026-09-19 Sat
      2026-09-20 Sun   2026-09-21 Mon   2026-09-22 Tue

  WHICH WINDOWS HAVE CLOSED. A window is only checkable once it has closed; an open
  window is not a gap, it is a job that still has time.

      daily_probe : 09-16 closes 2026-09-16T21:00:00Z  CLOSED
                    09-17 closes 2026-09-17T21:00:00Z  CLOSED
                    09-18 closes 2026-09-18T21:00:00Z  CLOSED
                    09-19 closes 2026-09-19T21:00:00Z  CLOSED
                    09-20 closes 2026-09-20T21:00:00Z  CLOSED
                    09-21 closes 2026-09-21T21:00:00Z  CLOSED
                    09-22 closes 2026-09-22T21:00:00Z  STILL OPEN at 04:00Z — skipped
      weekly_probe: 09-18 closes 2026-09-19T03:00:00Z  CLOSED   (the only Friday)

  So 6 daily windows and 1 weekly window are eligible, 7 in all.

  THE RECORDS. `daily_probe` has four, `weekly_probe` has none:

      #  fetched_at (UTC)        = ET wall clock        verdict
      -  ----------------------  ---------------------  --------------------------
      1  2026-09-16T14:00:00Z    09-16 10:00 ET         INSIDE 09-16's window
      2  2026-09-17T22:00:00Z    09-17 18:00 ET         OUTSIDE — one hour LATE
      3  2026-09-18T20:59:00Z    09-18 16:59 ET         INSIDE, one minute to spare
      4  2026-09-21T13:00:00Z    09-21 09:00 ET         INSIDE, exactly at the open

  Record 2 is the one that matters: the job RAN on 2026-09-17 and produced a file,
  and 2026-09-17 is still a gap, because the rule is "a record inside the window",
  not "a record on the day". A file that arrived after the window closed is not the
  observation the window was for.

  THE ANSWER. Four gaps, in `(date_et, job)` order:

      #  date (ET)    job            cadence  window closed (UTC)
      -  -----------  -------------  -------  --------------------
      1  2026-09-17   daily_probe    daily    2026-09-17T21:00:00Z
      2  2026-09-18   weekly_probe   weekly   2026-09-19T03:00:00Z
      3  2026-09-19   daily_probe    daily    2026-09-19T21:00:00Z
      4  2026-09-20   daily_probe    daily    2026-09-20T21:00:00Z

  The two jobs interleave — daily, weekly, daily, daily — which is what fixes the
  sort key as `(date_et, job)` and not "all of job A, then all of job B".

  Counting it the other way as a check: 7 eligible windows, 3 of them satisfied
  (daily 09-16, daily 09-18, daily 09-21), so 7 - 3 = 4 gaps. The two counts agree.

  AND NOTHING IS FILLED. There is no interpolation over 09-17, no carry-forward of
  09-16's file, and no estimate. The four lines are the entire output. The module
  has no `fill_gap`, no `backfill`, no `impute` and no `interpolate` — the test
  asserts the ABSENCE by name, because an assertion about behaviour that does not
  exist has to be an assertion about the namespace.

Case 4 — THE EXACT GAPS.md LINES
================================================================================
The file is append-only: `append_gaps` adds lines and never rewrites one, and a gap
already present is not appended a second time (its key is the leading
`| {date_et} | {job} |`). Logged at 2026-09-22T04:00:00Z, the four gaps of Case 3
produce exactly these four lines, in this order:

| 2026-09-17 | daily_probe | daily | 09:00-17:00 ET | 2026-09-17T21:00:00Z | no record in window | 2026-09-22T04:00:00Z |
| 2026-09-18 | weekly_probe | weekly | 15:30-23:00 ET | 2026-09-19T03:00:00Z | no record in window | 2026-09-22T04:00:00Z |
| 2026-09-19 | daily_probe | daily | 09:00-17:00 ET | 2026-09-19T21:00:00Z | no record in window | 2026-09-22T04:00:00Z |
| 2026-09-20 | daily_probe | daily | 09:00-17:00 ET | 2026-09-20T21:00:00Z | no record in window | 2026-09-22T04:00:00Z |

  Seven columns: date (ET), job, cadence, window (ET), window closed (UTC), reason,
  logged (UTC). The last column is when the line was written, which is NOT the same
  instant as the window close and is a different fact — it is how long the gap went
  unnoticed. On this run the difference is between 7 and 63 hours.

  Re-running `append_gaps` with the SAME four gaps at a later `logged` time appends
  NOTHING, and the file is byte-identical afterwards. Appending a fifth gap
  (2026-09-21, say) adds one line and leaves the four above untouched, byte for
  byte, including their original `logged` column.

================================================================================
What this ledger deliberately does not pin
================================================================================
  * No live URL, no network. Every byte above is a literal.
  * No strategy return, and no fixture row from 2024-01-01 on: the only dates here
    are the synthetic September 2026 schedule, which is a clock, not a price.
  * Not the health line's contents beyond its shape — it carries wall-clock
    durations and a host name, which are facts about one machine on one evening and
    have no business in a golden.
